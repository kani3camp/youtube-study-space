# Raw YouTube API data retention

## Purpose

This document separates raw data obtained from YouTube API Services from data generated by the Study Space service itself, and records the retention controls that must apply to each storage layer.

This is an engineering/data-governance document, not a substitute for the public Privacy Policy or Terms of Service.

## Raw YouTube live chat data

The YouTube bot reads text messages from YouTube Live Chat and stores each text message in Firestore `live-chat-history` before command processing.

A `LiveChatHistoryDoc` currently contains:

- YouTube author channel ID
- author display name
- author profile image URL
- moderator flag
- YouTube live chat message ID
- YouTube live chat ID
- message text
- published timestamp
- message type

This means normal chat messages are persisted even when they are not Study Space commands.

### Current storage path

```text
YouTube Live Chat API
        |
        v
Firestore: live-chat-history
        |
        | daily Firestore export
        v
Google Cloud Storage
        |
        v
BigQuery: firestore_export.live-chat-history
```

Firestore already has an application-level cleanup controlled by `collection-history-retention-days`, but the same flow copies the data to GCS/BigQuery first. Therefore Firestore deletion alone is not sufficient to enforce raw-data retention.

## Retention rule

Raw YouTube live chat data must not be retained by application-controlled stores for more than 30 calendar days.

The application therefore enforces a hard 30-day upper bound independently of the configurable retention used for Study Space history data.

After the daily BigQuery transfer:

1. Firestore `live-chat-history` documents older than 30 days are deleted.
2. BigQuery `firestore_export.live-chat-history` rows older than 30 days are deleted.
3. Study Space-owned collections are not affected by this hard limit.

Reference: YouTube API Services Developer Policies, Stored Data requirements:
https://developers.google.com/youtube/terms/developer-policies

## Study Space-owned data

The following data is produced by the service as part of its own functionality and is intentionally treated separately from the raw live-chat archive:

- `users`
- `user-activities`
- `work-segments`
- `order-history`
- active `seats` / `member-seats`
- seat-limit collections
- rank, accumulated work time, preferences and other user state

These records can contain a YouTube channel ID as the service's user identifier. They therefore still need a documented purpose, retention policy, and user-deletion process, but the raw-live-chat 30-day cap is not automatically applied to them.

## GCS follow-up required

The application reads Firestore export snapshots from GCS, but the repository does not define the export job or bucket lifecycle policy. The export bucket may also contain collections unrelated to live chat.

Do not blindly delete old export folders from application code. Before changing GCS retention:

1. inspect the production export bucket lifecycle configuration;
2. determine whether the bucket is a general disaster-recovery backup or only an analytics-transfer staging area;
3. identify whether snapshots older than 30 days still contain `live-chat-history` data;
4. either configure an appropriate lifecycle/selected-collection export, or move the raw-chat transfer to a dedicated short-lived bucket;
5. clean up historical raw live-chat snapshots once the safe migration path is established.

Until this is confirmed, GCS is the remaining storage-layer gap for raw live-chat retention.

## User deletion follow-up

A separate deletion workflow must be provided for users who request deletion of data related to their YouTube identity. It must cover raw live-chat data as well as Study Space-owned user data according to the public Privacy Policy and applicable YouTube API requirements.

The deletion workflow should be designed separately because it needs to account for Firestore, BigQuery, GCS backups, and the upcoming MyPage Firebase UID / YouTube channel ownership mapping.
