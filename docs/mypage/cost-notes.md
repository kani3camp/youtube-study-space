# MyPage 増分原価モデル

[cost-model.json](cost-model.json) の入力値と [cost-model.py](../../mypage/scripts/cost-model.py) を用いて、利用量・構成・集計方式を変えた場合のコスト試算を生成する仕組みです。

```sh
python3 mypage/scripts/cost-model.py --test
python3 mypage/scripts/cost-model.py --output /tmp/mypage-cost-report.md
# 感度パラメータを変える場合は入力の非公開コピーを作り --input で指定する
```

> [!NOTE]
> `verifiedAtJST` は価格調査日であり、現在の料金や実際の請求額を保証するものではありません。再利用時は対象リージョンと公式料金を再確認してください（出典は `cost-model.json` の `sources` に記載）。また、生成したレポートは作業資料として扱い、リポジトリへ重複保存しないでください。実請求との照合は [Issue #1133](https://github.com/kani3camp/youtube-study-space/issues/1133) で追跡します。

## 構成と入力パラメータの前提

- 採用構成は `hosting-run`（Firebase Hosting + Cloud Run API）です。`armor-run` は不採用の比較シナリオ（Cloud Armor + 外部 LB + Run Web/API）であり、スクリプトの先頭表はこの比較用感度表です（採用構成の試算値は `hosting-run` の行を参照してください。構築状態や承認済み予算を示すものではありません）。
- DAU・滞在時間・原記録件数・インデックスエントリー・月次検索平均・キャッシュヒット率・課金経過時間・転送量・再試行回数はすべて仮定の試算入力です。小規模な合成テストデータや端末側遅延を、利用者平均・Run CPU・実請求に一般化しないでください。
- 概要表示・セッション完了 POST・明細・全 Bot 利用者の月次書き込みを個別に加算しています（定期取得を 5 分間隔へ変えても、セッション数や App Check 評価回数が同じ割合で減るとは仮定していません）。
- 月次検索が最大 2 文書であっても API 全体が 2 read で済むわけではありません。認可確認・WebAccount・User・空の座席クエリの最低課金・メタデータ更新・トランザクション再試行・インデックスエントリー読み取り・キャッシュヒット時の認可読み取りを含めて評価します（`limit(1001)` はインデックス走査の課金上限ではなく、`Query Explain Analyze` 自体の実行も課金対象です。明細の重み付き利用枠は実読み取り数と区別し、失敗・ACK 不明・利用枠管理の増分も計上します）。
- Cloud Run / Hosting / App Check の扱い
  - Run の秒数は割当リソースの課金経過時間の仮定です（100 ms 単位の丸め・起動・同時実行数は別途確認）。
  - 静的キャッシュを有効にしても初回訪問・リリース更新時の再ダウンロードは残るため、HTML/API の `no-store` と分けて扱います。
  - App Check / reCAPTCHA は組織全体の評価回数に対する増分として計上し、定期取得とは独立に別プロジェクトの利用も確認します。

## 会計境界とモデル外の費用

- 無料枠の二重控除防止: Firestore 無料枠はプロジェクトの対象 DB・日単位、Cloud Run 無料枠は請求先アカウント全体で共有されます。Hosting は全サイト・チャネルと旧リリース保存量を合算するため、利用可能な残量を入力で明示して DEV / PROD で二重に差し引かないようにしてください（Hosting の GB と Firestore/LB の GiB も区別します）。
- 既存処理との切り分け: 既存処理は基準となる利益に含め、新しい Web 機能の増分だけを計算します。候補会費・手取り率・為替・税は仮定値であり価格決定の承認ではありません（アップグレードは既存会費との差額のみ加算し、Bot 書き込み・DEV 変動費・イメージ保存費は別途加算します）。
- モデル外の費用: ストレージ・インデックス・旧リリース・ログ保持・バックアップ/PITR・データ移行や削除・Auth / Identity Platform・Monitoring・YouTube クォータ・不正利用・税・手数料・返金は必要に応じて別途加算します。入力が `0` であっても無料になることを証明するものではなく、このモデルを請求総額や厳密な費用上限として扱わないでください。

実運用でのインスタンス上限・Budget 通知の実着信・異常利用監視の確認手順は [配備手順書](release/README.md) と [E2E 手順](release/e2e.md) を参照してください。
