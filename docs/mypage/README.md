## 設計の基本原則

- 本人の識別には YouTube チャンネル ID と同じ値の Firebase カスタムプロバイダー UID を使い、クライアントから対象チャンネル ID を受け取りません。
- OAuth コールバックの処理権確保と確認時の一度限りの消費は、それぞれアトミックに行います。外部 API の呼び出しとトークン発行はトランザクションの外で実行します。
- 現在・今日・月曜開始の週・生涯累計・直近 7 暦日の数値は、同じスナップショットと `asOf` 時刻に揃えます。
- 作業時間は秒単位で合計し、表示時だけ分に切り捨てます。取得障害やデータの矛盾を検出した場合は取得不能として扱います。
- アカウントのメタデータと作業統計の部分障害を分けて扱い、元の ID・認証情報・DB のパスはレスポンスやログに載せません。
- 初期公開のプライバシー受付は返信可能な人的窓口 → 非公開 CLI で `SupportRequest` 作成 → 依頼専用の新しい YouTube OAuth 認証（fresh OAuth） → 非公開手順で削除・連携解除・開示を実施する流れです（アプリ内受付・返信 UI と未接続 Operator OIDC は撤去済みで、実環境検証・D02/D03・削除確認項目の完了が別途必要です）。

### ローカルでの単体・仕様検証

実装と通信用の型はリポジトリのルートから次のコマンドで検証できます（基盤構築や本番への配備は含みません）。認証・本人切替・ServiceAccessControl の安全条件は Go / Vitest / Firestore Emulator テストで検証します。

```sh
(cd system && go test -shuffle=on ./core/mypage)
(cd mypage && pnpm test)
```

## 認証とサーバーの検証範囲

### Web 認証データの保存

サーバー専用コレクションとして `oauth-transactions/{opaque id}` と `web-accounts/{verified channel id}` を追加します。既存のセキュリティルールは既定で拒否するため、ブラウザからはアクセスできません。

- 有効期限（10 分）の判定はアプリケーション側で行います。TTL の定義とモック・限定的な plan の検査は [MyPage 専用 Terraform](../../infra/mypage-oauth-ttl/README.md) にあります（plan/apply、TTL の ACTIVE 状態と自然削除の観測、権限、削除処理の実環境確認は基盤構築の確認後に別途承認を受ける作業として残します）。
- コールバックでは `pending -> processing -> channel_verified`、確認では `channel_verified -> consumed` へ遷移し、`WebAccount` の作成・更新と消費は同じトランザクションで行います。
- `firstWebLoginAt` は認証済みセッション完了時に未設定の場合だけ記録し、Web ログインでは `users` や作業履歴を変更しません。
- トランザクションレコードには `state` のハッシュ・同意バージョン・公開チャンネルメタデータ・時刻だけを保存し、認可コード・OAuth トークン・Custom Token は保存しません。
- Google プロバイダーと Firebase トークン発行はインターフェースで分離し、`demo` エミュレーターでは合成プロバイダーを使います。

### YouTube OAuth プロバイダー

`GoogleYouTubeOAuth` は、サーバー専用のクライアント ID・シークレットと固定の HTTPS オリジンを受け取り、既存のアトミックなコールバック処理に接続するアダプターです。

- 認可には `youtube.readonly` だけを使い、`online` と `select_account` を指定します。Google アカウントの選択を YouTube チャンネルの選択とはみなしません。
- 認可コードの交換は 1 回だけ行い、付与されたスコープを検証してから、同じ短命のアクセストークンで `mine=true` のチャンネルを取得します。チャンネルがない場合・複数ある場合・次のページがある場合は拒否し、唯一のチャンネルの公開メタデータだけを返します（旧カスタム URL から `@handle` を推測しません）。
- インスタンス・ストア・レスポンスに YouTube トークンを保存せず、リフレッシュトークンも要求しません（`token source` による更新や再試行も行いません）。コールバックのオリジンをリクエストから作らず、外部へのリダイレクトも追わず、処理全体を 8 秒に制限します。
- プロバイダーのレスポンス本文や URL エラーは公開を許可したエラーに変換し、シークレット・認可コード・トークンは公開エラーに出しません。

一次資料: [Google OAuth server flow](https://developers.google.com/youtube/v3/guides/auth/server-side-web-apps) / [channels.list](https://developers.google.com/youtube/v3/docs/channels/list)

### DEV の OAuth 失敗診断

DEV サーバーのコールバック失敗は `mypage_oauth_failure stage=<固定値> code=<許可済みAPIコード>` として記録します（本番では接続しません）。

- `stage` は用途読み取り・メンテナンス確認・入力確認・処理権確保・拒否・プロバイダー解決・コード有無・トークン交換・scope 検証・token 検証・チャンネルリクエスト（構築/通信/status/decode）・チャンネル選択・失敗状態保存・確認参照生成・検証結果保存を区別します。Google のエラー理由の推測には使わず、たとえば `token_exchange` だけでは設定不備と通信失敗を区別できません。
- 診断イベントには固定の許可リスト（allowlist）にある段階名と公開エラーコードだけを渡します。認可コード・`state`・Cookie・トークン・クライアントシークレット・URL/クエリ・プロバイダーの本文や生エラー・アカウント/チャンネル/文書の識別子・任意文字列は渡しません。既存の認証検証・10 分期限・1 回のコード交換・公開エラー/リダイレクトは維持します。
- サーバーごとに最大 32 件の非ブロッキングキューを使い、単一のワーカーが出力します。キューが満杯の場合や、受信先不在・終了時は診断イベントを破棄してよく、認証の成否には影響させません。成功イベントは出さないため、完全な監査記録や失敗件数の正確な集計には使えません（ソース統合だけでは反映されず、承認済みの API 配備が必要）。

### Firebase の検証

#### FirebaseBoundary

公式 Admin SDK の `VerifyIDToken` / `CustomToken` インターフェースを使用します。署名検証済みのトークンに対して固定プロジェクトの `issuer` / `audience`、custom provider かつテナントなし、チャンネル形式の UID と `subject` の一致、期限・発行時刻・認証時刻を追加検証します（SDK やトークンのエラーは公開メッセージやログへ転記せず、発行処理にはサーバーが確認したチャンネル UID のみ渡す設計）。

#### AppCheckVerifier

RS256 署名・JWT type・標準 claim・JWKS キャッシュ/更新は公式 Firebase Admin Go SDK の `VerifyToken` へ委譲し、薄いラッパーで MyPage 固有の project number ベースの `issuer` / `audience`、Web App ID、必須 `iat` / `exp`、厳密な時刻境界だけを確認します。SDK の不正 claim 型による panic も固定の認証拒否へ変換し、トークンや依存先エラーは出力しません。初回 JWKS 取得は起動時の制限時間 10 秒以内に行い、ハンドラー構築時は I/O を行いません（SDK は project ID 文字列を `audience` へ連結するため、App Check 専用 App へ project number を渡し、Auth 用 App は project ID のままとします）。

独自の JWT パーサー・JWKS 取得/鍵サイズ制限・singleflight・未知 `kid` 再取得・6 時間後の独自失効は撤去し、鍵の信頼と更新は標準 SDK に一本化しました（採用中 SDK は公開 JWKS を起動時に取得して 6 時間ごとに更新し、未知 `kid` は拒否します。独自 HTTP クライアント注入や公開終了 API はありません）。署名/期限/環境/アプリ不一致の拒否は維持しており、DEV での起動・鍵更新時の可用性は次回配備受入で確認します。

一次資料: [App Check custom backend verification](https://firebase.google.com/docs/app-check/custom-resource-backend) / [Firebase ID token verification](https://firebase.google.com/docs/auth/admin/verify-id-tokens) / [custom token signing](https://firebase.google.com/docs/auth/admin/create-custom-tokens)

### サーバーと鍵を使わない SDK の組み立て

- `NewMyPageServer` では固定の環境・プロジェクト・アプリ・オリジン、`FirebaseBoundary`、OAuth プロバイダー、Firestore の Auth/Support ストア、読み取り専用のスナップショット/BFF を 6 本のエンドポイントに接続します。コンストラクターはシークレットや認証情報の取得、外部通信、待ち受け、通知を行いません。
- `NewKeylessFirebaseClient` は既存 ADC の token source と明示した同一プロジェクトの署名者メールアドレスを受け取り、公式 SDK に `ServiceAccountID` を指定して IAM のリモート署名を使います（認証情報 JSON・鍵ファイル・Auth エミュレーター・プロジェクト不一致は拒否）。テストでは合成 IAM トランスポートで `signBlob` を RSA 署名して検証していますが、必要な `iam.serviceAccounts.signBlob` は別途インフラで確認する事項であり、権限付与コードは含めません。
- `cmd/mypage-server` は Cloud Run 用の起動処理で、固定設定の検証と基盤準備条件を満たすまで ADC を取得しません（実サーバー初期化ではエミュレーターと認証情報ファイルを拒否）。設定値・シークレット・SDK エラー詳細はログに出さず、HTTP タイムアウト・ヘッダー制限と graceful shutdown を備えます（readiness フラグはレビューの代わりにならず、実起動や配備には別途承認が必要です）。
- Cloud Run に設定するサーバー専用項目は、環境・リージョン・プロジェクト番号・Web App ID・公開オリジン・ポリシーバージョン・署名者メールアドレス・OAuth クライアント ID/シークレットです（OAuth 共通シークレットは Secret Manager から供給し、Vite に渡しません）。

## 作業集計と履歴

### 外部処理に依存しない集計

- `WorkSnapshot` は同じ Firestore スナップショットから読み取るアダプターとの受け渡しに使います（読み取り時刻がない入力は受理しません）。
- 今日・今週（月曜開始）・直近 7 日は、取得した作業区間と進行中の作業を日本時間（JST）の各集計期間に切り分けて合計します。正常取得で対象の作業がなければ 0 分とします。
- 現在の書き込み処理は退室時に入室セッション分を `users.TotalStudySec` へ転記するため、入室中の累計は `TotalStudySec + SeatDoc.CumulativeWorkSec + work 状態の経過秒` となります。進行中の履歴区間には `CurrentSegmentStartedAt` を使い、作業名変更で終了した区間と重ねません。休憩中もそのセッションで完了した作業時間は累計に残します。
- 原記録の上限 1001 件への到達、取得・解析の失敗、重複・未来・負の作業区間、座席の不整合があれば、影響する指標は `workSec: null` と理由コードを返します（問題のない現在の状態・累計・アカウント情報は保持し、保存漏れが判明した場合はデータ不具合として調査します）。

### スナップショットの読み取りと書き込み順序

1. User の検索で `DocumentSnapshot.ReadTime` を取得してから JST の検索期間を決めます。
2. `users`・`seats`・`member-seats`・`work-segments` を同じ読み取り専用トランザクションで読みます（User がなくても `readTime` を保持し、座席と履歴のクエリは省略します）。
3. 座席は各区分 2 件、履歴は 1001 件で打ち切ります。
4. `work-segments` の検索条件は `user-id` 一致、`ended-at > window start`、`started-at < asOf` です。必要な複合インデックスは [クエリ仕様](query-index.json) と [Firebase 配備定義](../../firebase/firestore.indexes.json) の一致を仕様チェッカーで検証します（実環境への適用状態はリリース時に別途確認）。

座席の移動では旧区間の終了と新座席への入室に同じ遷移時刻を使います。休憩の開始時刻は新座席への入室前でも正当ですが、現在の区間は新座席への入室以降でなければなりません。過去の重複区間は推測で修復したり許容したりせず、影響する履歴指標を `DATA_INCONSISTENT` にします（独立した現在の状態と累計は利用可能な限り維持）。

### 更新範囲と Bot との責務

Bot は既存の座席遷移と原記録の保存を担当します。マイページのための同期月次書き込みは外しており、集約 API は古い月次切替マーカーがあっても原記録を読み取ります。個人情報削除を行う際は既存 writer の停止・完了待ちと残存する月次データの削除を運用手順に従って確認してください。

- 初回・ページ再読み込み・手動更新は通常の `GET /api/mypage` を使い、画面が表示中かつオンラインの間の 5 分更新は `GET /api/mypage?view=current` を使って原記録と月次履歴のクエリを省きます。
- 認可と回数制限は共通ですが、キャッシュと同時実行の集約は取得範囲ごとに分離しています。画面は入室状況と作業時間の基準時刻を別々に保持し、定期取得で集計を上書きしません。
- ただし、集計を最後に同期した応答の `generatedAt`（サーバー時刻）の JST 日付と定期取得時点のブラウザ時計の JST 日付が異なる場合は、次の定期取得（可視化・復帰時の取得を含む）で通常の `GET /api/mypage` を使って作業サマリーと直近 7 日を更新します。取得に成功するまで（または失敗して既存の値を保持している間）は次の定期取得でも全項目を再試行します（ブラウザ時計が日単位でずれている間は毎回全項目を取得しますが、時計が正しければ同じ日の定期取得は入室状況のみの更新に戻ります）。

## HTTP とキャッシュ

### エンドポイント境界と認可

`HTTPHandler` は通常ログイン用の 6 本のエンドポイントを提供するライブラリです。

- 統計へのアクセス前に App Check・Firebase custom provider・最新の ServiceAccessControl・`WebAccount` の存在と同意バージョンを検証します（キャッシュヒット時も毎回検証。旧 `accessBlocked` はデコード互換のためだけに残し、認可には使いません）。
- 推測できない Cookie には `HttpOnly` / `Secure` / `Lax` / `Path=/` を指定し、`Domain` は指定しません。コールバックは固定パスへリダイレクトし、プロバイダーの元のエラーや依存先の詳細を公開しません。
- OAuth トランザクションの文書がない場合は、TTL による削除・古い Cookie・存在しない ID を区別せず期限切れとも扱わずに、処理権確保の前に `/login?error=oauth_state_invalid` へ戻します。文書がないと目的を判別できないため、サポートフローでも受付画面ではなくログイン画面に戻ります。
- JSON は未知・重複・大小文字違いのフィールド、余分なクエリや本文、4096 バイト超を拒否します。
- 環境ごとに固定した HTTPS の `PublicOrigin` を必須とし、対象外の Host、別オリジンまたは Origin なしの POST、重複した Origin や `__session` は依存先検証や OAuth 状態変更の前に拒否します（コールバックの GET は Origin なしを許容しますが固定 Host 検証は省略しません）。クライアントの `X-Forwarded-Host` / `Proto` / `For` で許可先を変えず、`X-Forwarded-For` も判定に使いません（Hosting から届く実際の Host は配備時に確認）。

### 集計キャッシュと singleflight

- 集計キャッシュは環境と UID をキーにプロセス内メモリで最大 30 秒保持し、JST の日付境界を越えて再利用しません。`generatedAt` は元のスナップショットの値を維持し、失敗はキャッシュしません。
- メタデータは 24 時間で再取得の対象にします。再取得は共有処理の期限内で最大 3 秒かつ残り時間の半分までに制限し、YouTube 検索の 1 秒制限と Firestore の保存・再読み取り・アクセス再確認を同じ制限時間内に収めます（作業スナップショットの読み取り時間を残し、応答待ち時間は延ばしません）。
- 再取得に失敗した場合、取得から 30 日未満に限り一部取得として扱い、30 日以上は取得不能とします。認可エラーとチャンネル不在以外の失敗は、同じ UID・同じ `WebAccount` リビジョンについてプロセス内で 5 分間再取得せず既存のアカウント情報を同じ判定で返します（認可エラーとチャンネル不在は待機せず毎回再取得して判定し直します）。
- スナップショットの共有処理（singleflight）も元のリクエストの残り期限を引き継ぎ、最大 8 秒とレスポンス返却用の余裕で上限を決めます（認可前から消費している HTTP の制限時間をリセットしません）。最初の呼び出し元が切断しても他の呼び出し元の共有読み取りをキャンセルせず、共有処理内のメタデータコピーと呼び出し元の代替処理を分けます。
- 共有処理中に判明したチャンネル不在・メタデータの表示停止状態・認証検証エラーは同じリビジョンの呼び出し元に mutex で共有し、後から短い期限で合流した呼び出し元にも、永続データの消去に失敗した場合を含めて判明済みの表示停止状態を期限前に返します。最大 1024 件の singleflight 登録情報では登録・完了・スロット削除を同じロックで行います。

### レート制限

レート制限は検証済み UID 単位だけで、プロセス単位の上限付きメモリ（4096 キー）で管理します（`GET /api/mypage` は 10/min・burst 10、認証済みルート全体は 30/min・burst 15。超過時は `RATE_LIMITED` の 429 と正の `Retry-After` を返します）。配備全体の制限は未実装です。

- 未認証で到達できるルート（公開状態、ログイン開始、コールバック、チャンネル取得・確認）にアプリケーションのレート制限はありません。
- IP 単位の制限は置きません。2026-11-15 の DEV 実測で Cloud Run の `RemoteAddr` は Hosting 経由でも `run.app` 直接でも Google の内部アドレスとなり利用者を区別できず、IP 単位のバケットが利用者間で共有されて 6 人目のログイン開始が 10 分以内に 429 になるなど、過剰なリクエストを送るクライアントが他の利用者にも影響を与えました。`X-Forwarded-For` も Hosting 経由（右端から 2 番目が利用者 IP）と `run.app` 直接（右端が利用者 IP で左側は攻撃者が指定可能）で位置が異なり、1 段信頼では区別不能、2 段信頼では直接経路で偽装されて 4096 キー上限を枯渇させられるため、IP 制限とプロキシ段数設定を撤去し代わりのグローバル制限も置かないことにしました。
- 未認証リクエストの濫用は App Check と ID トークンの検証、認証後の UID 単位制限、Cloud Run の最大インスタンス数（本番 3・DEV 1）と同時実行数 40、OAuth トランザクションの 1 回限りのアトミックな消費で抑えます。
- [ServiceAccessControl A](service-access-control.md) は MyPage の読み取り・トークン発行・書き込みを保護し、横断削除・全ランタイムでの処理停止完了・サポート受付の完了処理は B の独立した完了条件とします。

## フロントエンドと画面遷移

### 個人データのメモリ管理

- `MyPageMemory` は UID 変更・ログアウト開始・`pagehide` 時に個人データを同期的に消去してリクエストを中断し、世代照合により遅れて届いたレスポンスも破棄します（ログアウトに失敗してもデータは復活せず再試行でき、初期化中はログイン画面を出しません）。
- MyPage の概要ルート（末尾スラッシュ含む）が表示中かつオンラインの場合だけ、取得成功から 5 分後に定期取得します（別ルート・非表示・オフライン時は停止し、復帰時は残り時間を待つか 5 分以上経過していれば即座に再取得）。初回取得・手動更新・重複防止・連打抑止を維持します。
- 通常の 503 に対する自動再試行の待機期限は絶対時刻で保持し、タブ・ルート・ネットワーク・bfcache 復帰で短縮しません（明示的な手動更新は可能ですが、429 の `Retry-After` では手動更新も待ちます。同じ UID の復帰には待機を引き継ぎます）。
- 401 ではデータを消去し同じ UID で一度だけトークンを更新します（App Check だけが原因の場合は一度再取得。401 継続・再同意・`WebAccount` 不存在では `signOut` に戻します）。取得できないセクションや指標は、同じ UID で直前に成功した値だけをメモリに保持し、元の `asOf` と古い値である旨を保持します（未取得を 0 にしません）。
- 利用制限の 403 では個人データを同期的に消去して専用表示へ移り、定期取得・手動更新・復帰時再試行を停止します（ログアウト・公開の法的文面・サポート・新たなログインは利用でき、通常の 503 における待機時間と古い値の表示は維持します）。
- `METADATA_TOO_OLD` では直前に取得成功したアカウント情報も消去して理由を示し、認証拒否後に `signOut` が失敗した場合は `LOGOUT_FAILED` と再試行手段を維持します。MyPage のレスポンスやメタデータをストレージに保存する処理は持ちません。

### ブラウザでの実行と合成統合テスト

- 通常ログインの `start` / `channel` / `confirm` / `session-complete`、Firebase custom sign-in、App Check と ID トークン付きの同一オリジン API、TanStack Router を接続します。対象 UID は Firebase から読み、クライアントから対象チャンネル ID を送りません。
- `confirm` は自動再送せず、Custom Token もメモリやストレージに保存しません。`session-complete` の一時失敗だけ最大 3 回試し、失敗時はその UID を `signOut` します（旧セッションの遅延処理で新しい UID を `signOut` せず、完了前は個人画面のデータ取得を抑止）。
- 公開 Firebase 設定とポリシーバージョンが揃わない場合はログイン不可とし、公開ページだけを表示します。Vite に OAuth シークレット・管理者認証情報・App Check デバッグトークンは設定せず、Firebase SDK による認証セッション永続化を除いて個人メタデータと作業データはメモリ内だけに置きます。
- Router のスクロール位置復元は無効化し URL をキーにしません（現在のライブラリは `pagehide` 時に空の `{}` を `sessionStorage` へ書きますが URL・チャレンジ・メタデータは含みません）。Cookie 名は前後の空白を正規化し、同名 Cookie の重複を拒否します。
- 認証とルートの合成 QA には [表示の受入条件](design/README.md) を使います（ランタイムが動くことと実環境での認証・公開受入完了は区別します）。

> [!NOTE]
> サポートの本人確認は準備中と明示し通常ログインへ進めず、privacy / terms / contact と Cookie 設定は未完成の草案 UI であり公開承認版ではありません（人間が決める運営者・窓口・公開 URL を推測で埋めません）。一般公開前には、実際の Google OAuth・Firebase App Check・Hosting 経由の E2E、承認済みランタイムとのピクセル一致、プライバシー/セキュリティ運用、D01 実装証拠・D02 規約適合性確認・D03 実値、基盤の準備完了確認が必要です（詳細は [配備手順](release/README.md) と [実経路 E2E](release/e2e.md)）。

### bfcache から確認画面への復帰

チャンネル確認画面で `pagehide` や本人の変更が起きたら処理待ちの確認を中断し、旧チャンネルを消去して中断理由とやり直しの導線を表示します。bfcache でマウント済み画面へ戻っても待機表示を続けず、旧成功応答による受付情報の復活や遷移を抑止します（通常ログインはログインからやり直し、サポートは受付窓口へ戻ります）。

実際の bfcache は HMR を含まない専用の静的ビルドで確認します（実行方法は [表示の受入条件](design/README.md)）。

### 表示・合成検証

表示原則・対象状態・ブラウザ QA は [表示の受入条件](design/README.md)、パッケージの検証コマンドは [mypage README](../../mypage/README.md) を参照してください。表示確認・ランタイム確認専用のエントリーポイントは本番ビルドに含めず、合成検証では外部リクエストを遮断して実ユーザーデータを成果物に保存しません。

## サポートの本人確認

### サポート記録の扱い

`FirestoreSupportStore` は運用担当者・サーバー用のライブラリであり、公開管理 API ではありません。

- 環境・リクエスト ID・対象チャンネル・目的（`delete`・`revoke`・`disclosure`）を記録し、チャレンジはハッシュと 24 時間の期限だけを保存します（同環境とリクエスト ID の重複作成はトランザクションで拒否）。
- チャレンジの再発行では元の受付時刻と削除期限（受付から 7 暦日）を維持して旧チャレンジのインデックスを削除し、期限超過後に再発行しても SLA を延長しません。
- `SupportBinding` はレコード参照・リクエスト ID・環境・目的・チャレンジハッシュを保持するサーバー専用の値であり、再発行前の対応づけ、目的・環境・対象チャンネルの不一致、期限境界、証拠の再利用を拒否します。本人確認に成功するとチャレンジを消費しますが、それだけで削除実行を承認するものではありません。完了レコードへの状態遷移ではチャンネル・チャレンジ・証拠・OAuth 参照を取り除いて匿名監査に必要な最小限の時刻だけを残します（D01 の削除保護は代替せず、既存の `users`・座席・履歴・Auth ユーザーを変更しません）。

### サポート OAuth のアトミックな処理

- `start` は任意項目 `supportChallenge` からサーバーのレコードを特定し、同じ Firestore トランザクションで有効な対応づけを確認して OAuth レコードを作ります（リクエスト ID・環境・目的・チャレンジハッシュを固定）。`channel` は固定された目的と新たな OAuth 認証で得た公開メタデータだけを返し、クライアントから対象チャンネルや目的を受け取りません。
- サポートの `confirm` では同じトランザクションで OAuth の状態・参照・同意バージョンと、受付レコードの状態・環境・リクエスト ID・目的・旧チャレンジ無効化・対象チャンネル・期限を検証します。`SupportRequest` に証拠を一度記録して OAuth とチャレンジを消費し、独立した 2 つの新しい OAuth トランザクションからでも同じ依頼の証拠は一度だけ記録します。成功レスポンスは `purpose=support` と推測できない `requestRef` を返し、Custom Token 発行・`WebAccount` 作成・Firebase セッション完了・ユーザーデータ削除は実行しません（通常ログインの消費処理への迂回も拒否し、消費時に OAuth 内のチャンネルメタデータ・`state`・参照を消去）。
- 通常のレスポンスも `purpose=login` を明示して OpenAPI の判別可能な共用体を検証しており、通常ログイン用アダプターはサポートのレスポンスを受け付けません（D01 実装証拠・D02 規約適合性確認・D03 実値・公開準備の確認は未完了）。

### サポートのブラウザ操作と有効期間

- サポートフロー開始時は既存の Firebase セッションがあっても通常 MyPage へリダイレクトせず新たな OAuth 認証を開始し、不正なチャレンジでは専用の無効表示を維持します。確認画面にはサーバーから受け取った目的と公開チャンネル名を示し、成功時は推測できない参照番号だけを受付画面のメモリに渡し（ルート離脱・`pagehide`・UID 変更で消去し URL やストレージに保存しない）、`signIn`・`session-complete`・削除実行は呼び出しません。
- 製品 HTML に `no-referrer` を指定しチャレンジ等のクエリが外部遷移時の Referer に載らないようにしています（基盤のアクセスログ・CDN・Hosting 設定の実確認は公開前のセキュリティ確認事項であり、サポート用 CLI と受付窓口の実値は未完了で公開配備していません）。
- サポートの `confirm` で処理待ちのリクエストは本人・ページのライフサイクル・確認操作の世代に結び付け、ログアウト・別 UID・同一 UID 再ログイン・`pagehide`・アンマウント・新しい確認操作で旧リクエストを中断し、`pageshow` でも復活させません（サーバーレコードの取消ではなくブラウザ側で無効な応答表示を抑止する処理）。

### 運用担当者向けの読み取り専用エミュレーター診断

`cmd/mypage-operator-dryrun` は合成データを使うローカルエミュレーターだけに接続する診断 CLI です。

- `development`・明示した `demo` プロジェクト・IP ループバックの接続先・目的（`delete` / `revoke` / `disclosure`）を必須とし、認証情報ファイル・実プロジェクト・本番・実行用引数を拒否します（受付参照はサイズ制限付きの標準入力だけから受け取り、引数やログに出しません。ADC・Google API・Auth 失効・通知・書き込みインターフェースは持ちません）。
- 同じ読み取り専用トランザクションでサーバーの受付レコード、消費済みサポート OAuth との対応、受付インデックスを照合します（通常ログイン、未確認レコード、不一致、期限切れは拒否。OAuth 追跡記録が TTL で除去されている場合は `proofTrace=unknown` とする診断だけを返します）。
- 出力は時刻・状態・目的・スコープ付き件数だけとし、チャンネル ID・受付 ID・チャレンジ・証拠・氏名・作業内容・元レコードや生エラーは出しません。文書 ID は最大 1001 件取得し 1000 件超は `at_least=1001`、取得失敗や未確認のストアは `unknown`（0 扱いしない）とします。また Auth・キャッシュ・バックアップ・エクスポート・BigQuery・ログ・旧方式・他受付の関連は未確認のため、`readOnly=true`、`executionAuthorized=false`、`inventoryComplete=false` を常に明示します。

```sh

MYPAGE_ENVIRONMENT=development MYPAGE_SUPPORT_PURPOSE=delete \
FIRESTORE_EMULATOR_HOST=127.0.0.1:8080 \
go run ./cmd/mypage-operator-dryrun < /path/to/private-synthetic-reference
```

参照ファイルは手元のアクセスを制限した場所に保持し、リポジトリ・PR・CI 成果物に追加しないでください。

## 任意のアクセス解析と同意

### 同意とセキュリティ文面の草案

- 任意のアクセス解析の状態は `unset` / `granted` / `denied` とし、`unset` では操作を妨げない選択画面を出します（拒否・未選択でも主要操作を利用できます）。選択した `granted` / `denied` 文字列だけをファーストパーティーストレージに保存し UID・チャンネル・プロフィールと結び付けず、`storage` イベントで別タブの拒否を受け取った場合も即座に送信を停止します（保存失敗時は現在ページの選択を適用しつつ保存失敗を表示）。
- `AnalyticsGate` は同意前に開始・送信せず過去イベントのキュー保存や再送もしません。固定ルート・タイトルと完全一致した公開 UTM の組み合わせだけを渡し、コールバック・`code`/`state`/`error`/`supportChallenge`・任意クエリ/フラグメント・`referrer`/`title` 入力・本人データを渡す API は持ちません（通常ログインの 4 イベントだけをパラメーターなしで扱います）。
- 実ローダーは測定 ID が設定され公開オリジンがブラウザのオリジンと一致する環境で同意後にスクリプトを読み込みます（必須の Firebase/App Check/reCAPTCHA 通信とは別同意）。公開ポリシーと利用規約の本文（privacy v1 / terms v1）は運営者が承認済みです。運営者の公開表記・窓口 URL・同意版・施行日はソースの定数で管理します。施行日は両文書とも初回本番公開日です（[公開設定](release/README.md#設定の受け渡し)）。
- 全 API レスポンスに `no-store` / `nosniff` / `no-referrer`、`default-src none` / `frame-ancestors none`、不要なデバイス権限の拒否を設定します（Hosting HTML の CSP 許可リストとコールバック基盤ログの秘匿処理は公開準備後に検証）。

### モックで検証できる GA4 コマンドアダプター

- `GA4Sender` は `AnalyticsGate` からだけ開始する同期的なアダプターであり、コンストラクターでは識別子やグローバル変数を作りません。開始時に `config` による自動ページビューと広告シグナルを無効化し、固定オリジンのルート URL・空の `referrer`・空の `title` を指定します。送信時も安全なルート・固定タイトル・許可済み UTM を再検証し、停止時はコンテキストを消去して測定無効化フラグを設定します（`denied` 変更時は送信を誘発し得る `gtag` コマンドを呼ばず、同意前イベントも再送しません）。
- モックで検証するのはコマンド引数と無効化順序だけであり、実 GA4 への非送信証明にはなりません。実ローダーでは同意世代変更後の遅延コールバック破棄が必要です。公開前には、`send_page_view=false` だけでは防げない Enhanced Measurement の履歴変更時自動ページビューの無効化、他タグ一覧、14 か月保持・保持期間リセット OFF、同意前/拒否後の非送信を確認します。

### 同意に連動する GA4 ローダー

- `ConsentTag` は `granted` の場合だけブラウザローダーを開始します。読み込み中に起きた同意後のイベント（ページ全体を読み込んだ直後に起きる最初のルートの `page_view` を含む）は gtag のキューへ渡し、同意前のイベントの保存・再送はしません（読み込みの失敗・タイムアウト・同意撤回・アンマウント時は送信を停止して保留コマンドを消し、旧読み込みの成否で新しい同意世代を変えません）。
- `browserTagLoader` は専用の単一 `dataLayer` を使い、スクリプト挿入前に安全な同意・設定を用意して固定の `gtag.js` URL・`no-referrer`・5 秒期限で読み込みます（共有タグやグローバル変数に既存所有者がいる場合は拒否し、撤回後の再同意時は読み込み済みスクリプトを再取得しません）。
- リリース設定には `VITE_MYPAGE_GA4_ID` と `VITE_MYPAGE_PUBLIC_ORIGIN` を必須とし、GA4 設定がないローカル環境ではタグを読み込みません（スクリプトを除去しても実行済みベンダーコードは取り消せないため、公開前に管理画面設定と実際の通信確認が必要です）。

## メタデータの保持と失効

### 公開チャンネルメタデータの更新

- 公開メタデータはサーバー専用 API キー（`MYPAGE_YOUTUBE_API_KEY` が設定されている場合のみ起動時に接続）を使って固定の YouTube エンドポイントから取得し、OAuth トークンは使いません。検索は 1 秒に制限し、リダイレクトを追わず、リクエスト URL や元のエラーを公開しません。
- 外部呼び出しはトランザクション外で行い、Firestore の実際の文書リビジョンとポリシー・アクセス状態をトランザクションで確認して既存アカウントの公開メタデータだけを更新します（新規作成はしません）。
- 取得から 30 日経過したメタデータは検索前に同じリビジョン保護処理で除去し、同意と本人情報は維持して `metadataFetchedAt` も消去します（認証や同意が失効した場合はスナップショット取得前に停止し、上流の取得失敗時は一部取得または取得不能として扱い、0 に変換しません）。
- メタデータの表示停止が必要と判明している場合は、作業スナップショットの取得・集計に失敗しても既存の 200 一部取得レスポンスでアカウントの `METADATA_TOO_OLD` を伝え、現在・集計・7 日すべてを `SOURCE_UNAVAILABLE` とします（スナップショットがない応答は生成時刻を使いキャッシュせず、通常の作業取得障害では 503 を維持）。ブラウザはこの理由を受け取ると旧アカウント情報だけを除去し、旧作業データと `asOf` は古い値として保持します。

### プロセス間でのメタデータ表示停止

- 公開 API が HTTP 200 で「明示的な `items=[]`」または「`items` が省略（`null` 含む）され `pageInfo.totalResults` が数値の 0」を返した場合だけチャンネル不在として扱います（YouTube Data API は 0 件時に `items` を省略し得るため `fields` に `pageInfo(totalResults)` を含めています。`{}`、`pageInfo`/`totalResults` の欠落・非数値・負数・非ゼロ、`nextPageToken` を伴う応答は一時的失敗として区別します）。
- 不在の場合は期限前でもリビジョン・ポリシー・アクセス状態を確認して公開メタデータと取得日時を消去し、消去に失敗しても不在と判明したメタデータはレスポンスに表示しません（通常の一時的失敗では許可された期限内の部分的メタデータを維持）。
- メタデータが空のアカウントは取得時刻消去済みの場合も含め `METADATA_TOO_OLD` で返し、BFF キャッシュと singleflight は `WebAccount` 文書のリビジョンとメタデータ有無に結び付けるため、他プロセスによる消去後の GET で旧キャッシュや旧リビジョンの共有処理は再利用しません（スナップショットの 30 秒・JST 日付境界の制約は維持。全ブラウザへの即時通知やアカウント削除に対するすべての書込み保護を提供するものではありません）。

### 未利用アカウントのメタデータ削除と監視

- `MetadataCleanupJob` は利用時の再取得とは独立して動作し、`metadataFetchedAt` が取得から 29 日以上のアカウントをページ単位で処理します。公開メタデータと取得日時の 4 フィールドだけを削除して `updatedAt` を更新し（未利用・`accessBlocked`・旧ポリシーにも適用）、本人情報・同意・`firstWebLoginAt`・アクセス状態は変更せず OAuth や API による再取得・アカウント作成も行いません。
- Firestore アダプターは明示したプロジェクトを確認し、時刻と文書 ID による安定したページ分割、最大 1001 件の検出、必要フィールドだけの取得、リビジョンの完全一致条件付きトランザクションを使います。並行更新された項目は上書きせず `changed`/`missing` として扱い、最終再走査でデータが残存した場合や、ページ上限・10 分の制限時間・各種失敗が発生した場合は成功扱いとせず、30 日以上のデータが残っていれば保持期限違反を匿名件数で記録します。
- `JSONMetadataCleanupRecorder` は匿名の開始・完了時刻、結果、固定段階名、件数だけを出力し（ID・メタデータ・元のエラーは含めず、監視出力の失敗自体もジョブの失敗とし、キャンセル後も 2 秒の制限時間内で記録を試みます）、書き込み期限を実際に適用できる専用パイプやソケット等だけを受け入れて通常ファイルや標準出力は拒否します。
- `EvaluateMetadataCleanupHealth` は成功実績なし、実行失敗、保持期限違反、成功した走査の `StartedAt` から 23 時間以上のハートビート欠如を警告します。29 日経過時点での対象抽出と処理時間の余裕を考慮し、接続時は成功した走査の開始間隔を 23 時間以内（例として 1 日 2 回）、ジョブを 10 分以内にする想定ですが、実スケジューラーや警告設定はまだ作成していません。
- 定期呼び出し側の [MetadataCleanupRunner](../../system/core/mypage/metadata_cleanup_runner.go) は `Run`（ジョブ + 監視永続化 + 健全性シグナル）とアカウントに触れない独立監視 `CheckHealth` を持ち、起動漏れ検知のため別々に起動する想定です。[FirestoreMetadataCleanupMonitor](../../system/core/mypage/metadata_cleanup_monitor_store.go) はサーバー専用の `mypage-maintenance/metadata-cleanup` 単一文書へ最新観測・成功走査の開始時刻・未受理の期限違反開始時刻をマイクロ秒精度に正規化して保存し、破損状態は初期化せず拒否、期限違反は出力先の受理後に想定時刻を比較するトランザクションで ACK します。

コールバックの接続例と残る運用上の依存事項は [メタデータ監視の実装・接続手順](release/metadata-monitoring.md) を参照してください。

## Hosting

`mypage/src/hosting.ts` の `hostingCandidate` は明示した環境・プロジェクト・対象・Cloud Run サービス・リージョン（`development` は `asia-southeast2`、`production` は `asia-northeast2`）とレビュー済みの SDK 接続先から設定候補だけを生成する純粋関数です。既存の `firebase/firebase.json` は変更せず CLI の `init`/`deploy` も実行せず、`public=dist` は `mypage` ディレクトリを基準にします。

- ルーティング: `/privacy_policy` は `/privacy` へ HTTP 302 転送、`/api` と `/api/**` は Cloud Run へ、`/privacy` と `/terms` はビルド時に生成した規約 HTML へ書き換え、残りは SPA へ書き換えます。
- キャッシュとヘッダー: 既定では全パスに `no-store` / `no-referrer` / CSP とセキュリティヘッダーを設定し、`hostingCandidate(input, assetPaths)` に検証済みの実ビルド全ファイル一覧を渡した場合だけ既知のハッシュ付き JS・CSS・`woff2` の完全一致パスを `public immutable` にします（HTML・API・未知のハッシュパスの SPA 代替表示は `no-store`）。
- セキュリティ境界: CSP は明示した HTTPS 接続先だけを許可し、`wildcard` / `unsafe-inline` / `eval` / 認証情報 / クエリ / フラグメントを拒否します。Firebase・App Check・reCAPTCHA の実接続先を推測せず、アクセス解析の接続先には別の承認が必要です。`validateHostingAssets` は静的ファイルと API の衝突・ソースマップ・秘密ファイル向けパスを拒否し、Cloud Run API 自身のレスポンスヘッダーも保持します。

原価の仮定と除外範囲は [増分原価モデル](cost-notes.md) を参照してください。CSP は基盤のログを制御しないため、実 SDK・reCAPTCHA・GA4 の通信一覧、Hosting の Host・ヘッダー・コールバック・アクセスログ除外、カスタムドメインの HSTS は対象リリースで別途検証します。
