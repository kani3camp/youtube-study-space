## 設計の基本原則

- **本人識別は YouTube チャンネル ID に固定**: Firebase のカスタムプロバイダー UID に YouTube チャンネル ID と同じ値を使います。クライアントから対象チャンネル ID を受け取ることはありません。
- **OAuth の状態遷移はトランザクションで保護**: コールバック時の処理権確保と、確認時の一度限りの消費をそれぞれアトミックに行います。外部 API の呼び出しやトークン発行はトランザクションの外で実行します。
- **集計期間と基準時刻の一貫性**: 「現在・今日・今週（月曜開始）・累計・直近 7 暦日」の数値は、同じスナップショットと `asOf` 時刻に揃えます。
- **作業時間の丸めと異常時の扱い**: 内部では秒単位で合計し、表示時に分へ切り捨てます。取得障害やデータの矛盾を検出した場合は `0` 分とせず「取得不能」として扱います。
- **障害の切り分けと秘匿**: チャンネル情報（メタデータ）と作業統計の部分障害を分けて扱います。元の ID・認証情報・DB パスはレスポンスにもログにも出しません。
- **プライバシー請求の初期運用**: ログイン不要の有人窓口で受け付け、非公開 CLI で `SupportRequest` を作成したうえで、その依頼専用の新しい YouTube OAuth 認証（fresh OAuth）で本人確認を行い、非公開手順で削除・連携解除・開示を実施します（アプリ内の受付・返信 UI と未接続の Operator OIDC は撤去済み）。

### ローカルでの単体・仕様検証

リポジトリのルートから次のコマンドでバックエンドとフロントエンドを個別に検証できます（基盤構築や実環境配備は含みません）。

```sh
(cd system && go test -shuffle=on ./core/mypage)
(cd mypage && pnpm test)
```

## 認証とサーバーの検証範囲

### Web 認証データの保存

サーバー専用コレクションとして `oauth-transactions/{opaque id}` と `web-accounts/{verified channel id}` を使用します。既存の Firestore セキュリティルールは既定で拒否するため、ブラウザから直接読み書きできません。

- **トランザクションの有効期限**: 作成から 10 分間です。有効期限の判定はアプリケーション側で行います。Firestore TTL による自然削除の定義・モック検査は [MyPage 専用 Terraform](../../infra/mypage-oauth-ttl/README.md) にあります（実環境での `plan` / `apply`・TTL の `ACTIVE` 確認・自然削除の観測は別途承認後に実施します）。
- **状態遷移**:
  - コールバック時: `pending` → `processing` → `channel_verified`
  - 確認時: `channel_verified` → `consumed`（同じトランザクション内で `WebAccount` を作成・更新）
- **記録するデータと記録しないデータ**:
  - `firstWebLoginAt` は認証済みセッション完了時に、未設定の場合だけ記録します。Web ログインでは `users` コレクションや作業履歴を変更しません。
  - トランザクションレコードには `state` のハッシュ、同意バージョン、公開チャンネルメタデータ、時刻だけを保存し、認可コード・OAuth トークン・Custom Token は保存しません。
- **開発時の差し替え**: Google プロバイダーと Firebase トークン発行はインターフェースで分離しており、`demo` エミュレーター環境では合成プロバイダーを使います。

### YouTube OAuth プロバイダー

`GoogleYouTubeOAuth` は、サーバー専用のクライアント ID・シークレットと固定の HTTPS オリジンを受け取り、アトミックなコールバック処理に接続するアダプターです。

- **認可パラメータ**: スコープは `youtube.readonly` のみを要求し、`access_type=online` と `prompt=select_account` を指定します。Google アカウントの選択をもって YouTube チャンネルの選択とはみなしません。
- **チャンネル取得の制約**: 認可コードの交換は 1 回だけ行い、付与されたスコープを検証したうえで、同じ短命アクセストークンで `mine=true` のチャンネルを取得します。チャンネルが 0 件・複数件・次ページあり（`nextPageToken`）の場合は拒否し、唯一のチャンネルの公開メタデータだけを返します。旧カスタム URL から `@handle` を推測しません。
- **非保持とタイムアウト**: トークンをインスタンス・ストア・レスポンスに保存せず、リフレッシュトークンも要求しません（`token source` による自動更新や再試行も行いません）。コールバックのオリジンをリクエストから組み立てず、外部リダイレクトも追わず、処理全体を **8 秒以内** に制限します。
- **エラー変換**: プロバイダーのレスポンス本文や URL エラーは許可された公開エラーに変換し、シークレット・認可コード・トークンを外部に出しません。

一次資料: [Google OAuth server flow](https://developers.google.com/youtube/v3/guides/auth/server-side-web-apps) / [channels.list](https://developers.google.com/youtube/v3/docs/channels/list)

### DEV 環境の OAuth 失敗診断

開発（DEV）サーバーでコールバックが失敗したときは、`mypage_oauth_failure stage=<固定値> code=<許可済みAPIコード>` 形式でログを記録します（本番環境では接続しません）。

- **`stage` の役割**: 用途読み取り・メンテナンス確認・入力確認・処理権確保・拒否・プロバイダー解決・コード有無・トークン交換・scope 検証・token 検証・チャンネルリクエスト（構築 / 通信 / status / decode）・チャンネル選択・失敗状態保存・確認参照生成・検証結果保存のどこで止まったかを区別します。Google 側の具体的なエラー理由を推測するものではありません（例: `token_exchange` だけでは設定不備と通信失敗を区別できません）。
- **秘匿境界**: 診断イベントに渡すのは固定 allowlist の段階名と公開エラーコードだけです。認可コード・`state`・Cookie・トークン・クライアントシークレット・URL / クエリ・プロバイダーの生エラー本文・アカウントや文書の ID・任意文字列は渡しません。既存の認証検証・10 分期限・1 回限りのコード交換・公開エラーとリダイレクト挙動はそのまま維持します。
- **非同期キュー**: サーバーごとに最大 32 件の非ブロッキングキューを持ち、単一ワーカーが出力します。キュー満杯時や終了時は破棄でき、認証の成否には影響しません。成功イベントは出さないため、監査記録や正確な失敗件数の集計には使えません。

### Firebase の検証

- **`FirebaseBoundary`**: 公式 Admin SDK の `VerifyIDToken` / `CustomToken` を使用します。署名検証済みのトークンに対し、以下を追加検証します。
  - 固定プロジェクトの `issuer` / `audience`
  - カスタムプロバイダーであり、テナントが存在しないこと
  - チャンネル形式の UID と `subject` の一致
  - 有効期限・発行時刻・認証時刻
  - SDK やトークンの生エラーは公開メッセージやログへ転記せず、トークン発行にはサーバーが確認したチャンネル UID だけを渡します。
- **`AppCheckVerifier`**: RS256 署名・JWT type・標準 claim・JWKS キャッシュと更新は公式 Firebase Admin Go SDK の `VerifyToken` へ委譲します。薄いラッパーで以下だけを追加検証します。
  - MyPage 固有の project number ベースの `issuer` / `audience`
  - Web App ID、必須の `iat` / `exp`、厳密な時刻境界
  - SDK が不正な claim 型で panic した場合も固定の認証拒否へ変換し、トークンや依存先の生エラーを出力しません。
  - 初回 JWKS 取得は起動予算 10 秒以内に行い、ハンドラー構築時は I/O を行いません。SDK は project ID 文字列を `audience` へ連結する仕様のため、App Check 専用 App には project number を渡します（Auth 用 App は project ID のまま）。
- **SDK 標準化**: 独自の JWT パーサー・JWKS 取得/鍵サイズ制限・singleflight・未知 `kid` 再取得・6 時間後の独自失効は撤去し、鍵管理を標準 SDK に一本化しています。採用中の SDK は起動時に JWKS を取得して 6 時間ごとに更新し、未知の `kid` は拒否します（独自 HTTP クライアント注入や公開の終了 API はありません）。署名・期限・環境・アプリ不一致の拒否条件は変わっていません。DEV 環境での起動・鍵更新時の可用性は実環境配備時に確認します。

一次資料: [App Check custom backend verification](https://firebase.google.com/docs/app-check/custom-resource-backend) / [Firebase ID token verification](https://firebase.google.com/docs/auth/admin/verify-id-tokens) / [custom token signing](https://firebase.google.com/docs/auth/admin/create-custom-tokens)

### サーバーと鍵を使わない SDK の組み立て

- **`NewMyPageServer`**: 固定の環境・プロジェクト・アプリ・オリジン、`FirebaseBoundary`、OAuth プロバイダー、Firestore の Auth / Support ストア、読み取り専用のスナップショット / BFF を 6 本のエンドポイントに接続します。コンストラクター自体はシークレット取得・外部通信・待ち受け・通知を行いません。
- **`NewKeylessFirebaseClient`**: 既存 ADC のトークンソースと同一プロジェクトの署名者メールアドレスを受け取り、公式 SDK に `ServiceAccountID` を指定して IAM のリモート署名を使用します。認証情報 JSON・鍵ファイル・Auth エミュレーター・プロジェクト不一致は拒否します。テストでは合成 IAM トランスポートで `signBlob` を RSA 署名して検証していますが、実 IAM の呼び出しや `iam.serviceAccounts.signBlob` 権限付与は別途インフラ側で確認します。
- **`cmd/mypage-server`**: Cloud Run 用の起動処理です。固定設定の検証と基盤準備フラグ（`MYPAGE_INFRASTRUCTURE_READY`）を確認するまで ADC を取得せず、実サーバー起動時はエミュレーターや認証情報ファイルを拒否します。設定値・シークレット・SDK エラー詳細をログに出さず、HTTP タイムアウト・ヘッダー制限・graceful shutdown を備えます。
- **Cloud Run のサーバー専用設定**: 環境・リージョン・プロジェクト番号・Web App ID・公開オリジン・ポリシーバージョン・署名者メールアドレス・OAuth クライアント ID / シークレットを設定します。OAuth シークレットは承認済みの Secret Manager 経由で供給し、Vite 側へは渡しません。

## 作業集計と履歴

### 外部処理に依存しない集計

- **`WorkSnapshot`**: 同一の Firestore スナップショットから読み取るアダプターと結果をやり取りします。スナップショットの読み取り時刻がない入力は受け付けません。
- **集計ロジック**: 今日・今週（月曜開始）・直近 7 日は、取得した作業区間と進行中の作業を日本時間（JST）の各期間に切り分けて合計します。正常に取得できて作業がなければ `0` 分となります。
- **入室中の累計計算**: 既存の書き込み処理は退室時にセッション分を `users.TotalStudySec` へ転記するため、入室中の累計は `TotalStudySec + SeatDoc.CumulativeWorkSec + work 状態の経過秒` で求めます。進行中の区間には `CurrentSegmentStartedAt` を使い、作業名変更で終了した区間とは重ねません。休憩中もそのセッションで完了した作業時間は累計に含みます。
- **異常時のフォールバック**: 原記録の上限（1,001 件）への到達、取得・解析の失敗、重複・未来・負の作業区間、座席の不整合があった場合、影響する指標は `workSec: null` と理由コードを返します。問題のない現在の状態・累計・アカウント情報はそのまま返します。保存漏れが判明した場合はデータ不具合として調査します。

### スナップショットの読み取りと書き込み順序

1. User の検索時に `DocumentSnapshot.ReadTime` を取得し、その時刻から JST の検索期間を決定します。
2. `users`、`seats`、`member-seats`、`work-segments` を同じ読み取り専用トランザクションで読み取ります。User が存在しない場合も `readTime` は保持し、座席・履歴のクエリは省略します。
3. 取得上限は座席が各区分 2 件、履歴が 1,001 件です。
4. `work-segments` の検索条件は `user-id == uid`、`ended-at > window start`、`started-at < asOf` です。必要な複合インデックスは [query-index.json](query-index.json) と [firebase/firestore.indexes.json](../../firebase/firestore.indexes.json) の一致を仕様チェッカーで検証します（実環境への適用状態はリリース時に確認します）。

座席移動時は旧区間の終了と新座席への入室に同じ遷移時刻を使います。休憩の開始時刻が新座席への入室前であっても正当ですが、現在の作業区間は新座席への入室以降でなければなりません。過去の重複区間は推測で修復せず、該当指標を `DATA_INCONSISTENT` とします。

### 更新範囲と Bot との責務

- **Bot との分担**: Bot は従来どおり座席遷移と原記録を保存します。MyPage 向けの同期的な月次書き込みは行わず、集計 API は古い月次切替マーカーが残っていても原記録を直接読みます。個人情報削除時は、既存 writer の停止・完了待ちと残存する月次データの削除を運用手順に従って確認します。
- **初回・手動更新と定期更新の使い分け**:
  - 初回表示・再読み込み・手動更新: `GET /api/mypage`（全項目を取得）
  - 概要画面が表示中かつオンラインの間の 5 分ごとの定期更新: `GET /api/mypage?view=current`（原記録と月次履歴のクエリを省略）
  - 認可と回数制限は共通ですが、キャッシュと同時実行の集約（singleflight）は取得範囲ごとに分離しています。画面側も入室状況と作業時間の基準時刻を別々に保持し、定期取得で作業集計を上書きしません。
- **JST 日付跨ぎの自動再同期**: 最後に集計を同期した `generatedAt`（サーバー時刻）の JST 日付と、定期取得時点のブラウザ時計の JST 日付が異なる場合は、次の定期取得（タブ可視化・復帰時を含む）で通常の `GET /api/mypage` を呼び、作業サマリーと直近 7 日を更新します。取得に成功するまで（または失敗して古い値を保持している間）は次の定期取得でも全項目を再試行します。ブラウザ時計が日単位でずれている間は毎回全項目を取得しますが、時計が正しければ同じ日の定期取得は `view=current` のみに戻ります。

## HTTP とキャッシュ

### エンドポイント境界と認可

`HTTPHandler` は通常ログイン用の 6 本のエンドポイントを提供します。

- **先頭での必須検証**: 統計データへアクセスする前に、App Check、Firebase custom provider、最新の ServiceAccessControl、WebAccount の存在と同意バージョンを毎回検証します（キャッシュヒット時も省略しません）。旧 `accessBlocked` はデコード互換のためだけに残し、認可には使いません。
- **Cookie とリダイレクト**: 推測不能な Cookie には `HttpOnly` / `Secure` / `Lax` / `Path=/` を付与し、`Domain` は指定しません。コールバックは固定パスへリダイレクトし、プロバイダーの生エラーや依存先の詳細を公開しません。
- **OAuth トランザクション不在時の扱い**: TTL による削除・古い Cookie・存在しない ID を区別せず、期限切れとも扱わずに処理権確保の前で `/login?error=oauth_state_invalid` へ戻します。レコードがないと目的（ログインかサポートか）を判別できないため、サポートフローであっても受付画面ではなくログイン画面へ戻ります。
- **入力の厳格検証**: JSON は未知・重複・大文字小文字違いのフィールド、余分なクエリや本文、4,096 バイト超を拒否します。
- **オリジン・Host の厳格検証**: 環境ごとに固定した HTTPS の `PublicOrigin` を必須とします。対象外の `Host`、別オリジンまたは `Origin` なしの `POST`、重複した `Origin` や `__session` は、依存先検証や OAuth 状態変更より前に拒否します。コールバックの `GET` のみ `Origin` なしを許可しますが、固定 `Host` の検証は行います。クライアントからの `X-Forwarded-Host` / `Proto` / `For` で許可先を変えず、`X-Forwarded-For` も判定に使いません（Hosting 経由で届く実際の `Host` は配備時に確認します）。

### 集計キャッシュと singleflight

- **メモリキャッシュ**: 環境と UID をキーにプロセス内メモリで最大 30 秒保持します。JST の日付境界を跨いで再利用せず、`generatedAt` は元のスナップショットの値を維持し、失敗結果はキャッシュしません。
- **メタデータの再取得とバックオフ**:
  - 取得から 24 時間経過したメタデータは再取得の対象になります。
  - 再取得は共有処理の期限内で **最大 3 秒かつ残り時間の半分まで** に制限し、YouTube 検索の 1 秒制限と Firestore の保存・再読み取り・アクセス再確認を同じ予算に含めます。作業スナップショットの読み取り時間を確保するため、応答待ち時間は延ばしません。
  - 再取得に失敗した場合、取得から 30 日未満なら「一部取得」、30 日以上なら「取得不能」として扱います。
  - 認可ゲートエラーとチャンネル不在以外の失敗については、同じ UID・同じ WebAccount リビジョンの再取得をプロセス内で 5 分間スキップし、既存のアカウント情報を返します。認可ゲートエラーとチャンネル不在は毎回再取得して判定し直します。
- **プロセス間の期限・状態共有**:
  - スナップショットの共有処理（singleflight）は元のリクエストの残り期限を引き継ぎ、最大 8 秒からレスポンス返却用の余裕を差し引いた時間を上限とします（認可前から進んでいる HTTP 制限時間をリセットしません）。
  - 最初の呼び出し元が切断しても、相乗りしている他の呼び出し元の共有処理は中断しません。共有処理側のメタデータコピーと呼び出し元のフォールバック処理は分離しています。
  - 共有処理中に判明したチャンネル不在・表示停止状態（`METADATA_TOO_OLD` 等）・認証検証エラーは、同じリビジョンの呼び出し元に mutex で共有し、後から短い期限で合流した呼び出し元にも判明済みの表示停止状態を期限前に返します。
  - singleflight 登録は最大 1,024 件とし、登録・完了・スロット削除を同じロックで行って取りこぼしを防ぎます。

### レート制限

- **対象と上限**: 検証済み UID 単位で、プロセス内のメモリ（上限 4,096 キー）により制限します。
  - `GET /api/mypage`: 10 回/分（バースト 10）
  - 認証済みルート全体: 30 回/分（バースト 15）
  - 超過時は `429 RATE_LIMITED` と正の `Retry-After` を返します（配備全体での分散制限は未実装）。
- **未認証ルートと IP 制限を設けない理由**:
  - 未認証で到達できるルート（公開状態、ログイン開始、コールバック、チャンネル取得・確認）にアプリケーション側のレート制限はありません。
  - 2026-11-15 の DEV 実測で、Cloud Run の `RemoteAddr` は Hosting 経由・`run.app` 直接のどちらでも Google 内部アドレスとなり利用者を区別できませんでした。また `X-Forwarded-For` も Hosting 経由（右から 2 番目が利用者 IP）と直接経路（右端が利用者 IP で左側はクライアントが偽装可能）で位置が異なるため、一律の信頼段数では他者の巻き込みや偽装による制限テーブル枯渇（4,096 キー上限）を防げません。
  - このため IP 制限とプロキシ段数設定は撤去し、未認証リクエストの濫用は App Check・ID トークン検証・認証後の UID 制限・Cloud Run の最大インスタンス数（本番 3 / DEV 1）と同時実行数（40）・OAuth トランザクションの 1 回限りの消費で抑止します。
- **ServiceAccessControl との役割分担**: [ServiceAccessControl A](service-access-control.md) は MyPage の読み取り・トークン発行・書き込みを保護します。横断削除・全ランタイム停止完了・サポート受付の完了処理は B の完了条件として分けて管理します。

## フロントエンドと画面遷移

### 個人データのメモリ管理

- **即時消去と世代管理**: `MyPageMemory` は UID 変更・ログアウト開始・`pagehide` 時に個人データを同期的に消去し、進行中のリクエストを中断します。世代を照合するため、中断後に遅れて届いたレスポンスは破棄されます。ログアウトに失敗してもデータは復活せず、再試行できます。初期化完了前はログイン画面を表示しません。
- **定期更新（5 分間隔）**: 概要ルート（末尾スラッシュ含む）が表示中かつオンラインの場合だけ、取得成功の 5 分後に再取得します。別ルート・非表示・オフライン時は停止し、復帰時に経過時間をみて残り時間を待つか即座に再取得します。重複リクエストや連打は抑止します。
- **エラー時の待機とフォールバック**:
  - 通常の `503` の自動再試行待機期限は絶対時刻で管理し、タブ復帰や bfcache 復帰で短縮しません（明示的な手動更新は可能）。`429` の `Retry-After` 中は手動更新も待機させます。待機期限は同じ UID にだけ引き継ぎます。
  - `401` 時はデータを消去し、同じ UID で 1 度だけトークンを更新します（App Check のみが原因なら 1 度再取得）。再同意必要・`401` 継続・WebAccount 不在時は `signOut` へ戻します。
  - 取得失敗したセクションは同じ UID で直前に成功した値だけをメモリに保持し、元の `asOf` と古い値であることを表示します（未取得を `0` にしません）。
  - 利用制限の `403` 時は個人データを同期的に消去して専用表示へ移り、定期・手動・復帰時の再試行をすべて停止します（ログアウト・法的文面・サポート・新たなログインは利用可能）。
  - `METADATA_TOO_OLD` 時は直前に成功したアカウント情報も消去して理由を表示します。認証拒否後の `signOut` 失敗時は `LOGOUT_FAILED` と再試行ボタンを表示します。
- **永続化の禁止**: MyPage のレスポンスやメタデータをブラウザストレージに保存しません（Firebase SDK による認証セッション永続化を除く）。

### ブラウザでの実行と合成統合テスト

- **ログイン経路**: `start` → `channel` → `confirm` → `session-complete` → Firebase custom sign-in を接続し、App Check と ID トークンを付けて同一オリジン API を呼びます。対象 UID は Firebase から読み、クライアントから対象チャンネル ID を送りません。`confirm` は自動再送せず、Custom Token もメモリやストレージに保存しません。`session-complete` は一時的な失敗だけ最大 3 回試行し、失敗時はその UID を `signOut` します（旧セッションの遅延処理で新しい UID を `signOut` しません）。完了前は個人画面のデータ取得を抑止します。
- **設定不備時の安全側動作**: 公開 Firebase 設定とポリシーバージョンが揃わない場合はログイン不可とし、公開ページのみ表示します。Vite ビルドには OAuth シークレット・管理者認証情報・App Check デバッグトークンを含めません。
- **ルーティングと Cookie 正規化**: TanStack Router のスクロール復元は無効化し、URL をキーにしません（ライブラリ仕様で `pagehide` 時に空オブジェクト `{}` が `sessionStorage` に書かれますが、URL・チャレンジ・メタデータは含みません）。Cookie 名は前後の空白を正規化し、同名 Cookie の重複を拒否します。

> [!NOTE]
> 合成 QA の実行方法は [表示の受入条件](design/README.md) を参照してください。
> サポート本人確認の実装や公開文面は段階的に整備中の部分を含みます。一般公開前には、実環境での Google OAuth・Firebase App Check・Hosting 経由 E2E、表示確認、プライバシー・セキュリティ運用、D01/D02/D03 の確定、基盤の準備完了確認が必要です（詳細は [配備手順](release/README.md) と [実経路 E2E](release/e2e.md)）。

### bfcache から確認画面への復帰

チャンネル確認画面で `pagehide` やユーザー変更が起きると、処理待ちの確認を中断して旧チャンネル情報を消去し、中断理由と再開始の導線を表示します。bfcache からマウント済み画面に戻った場合も待機表示を続けず、遅延して届いた旧応答による復活や遷移を抑止します（通常ログインは `/login` へ、サポートは `/contact` へ戻します）。

実際の bfcache 挙動は HMR を含まない静的ビルドで確認します（手順は [表示の受入条件](design/README.md)）。

### 表示・合成検証

表示原則や Playwright によるブラウザ QA は [表示の受入条件](design/README.md)、パッケージのコマンドは [mypage/README.md](../../mypage/README.md) を参照してください。表示確認用のエントリーポイント（`visual.tsx`）は本番ビルドに含めません。合成検証では外部リクエストを遮断し、実ユーザーデータを成果物に保存しません。

## サポートの本人確認

### サポート記録の扱い

`FirestoreSupportStore` は運用担当者・サーバー用のストアであり、公開管理 API は持ちません。

- **記録内容と有効期限**: 環境・リクエスト ID・対象チャンネル・目的（`delete` / `revoke` / `disclosure`）を記録します。チャレンジはハッシュと 24 時間の有効期限だけを保存します。同一環境・リクエスト ID の重複作成はトランザクションで拒否します。
- **再発行と期限の固定**: チャレンジ再発行時は、元の受付時刻と削除期限（受付から **7 暦日**）を維持し、旧チャレンジのインデックスを削除します。期限超過後に再発行しても SLA は延長しません。
- **値の境界**: `SupportBinding` はサーバー専用の値であり、再発行前の対応づけ、目的・環境・対象チャンネルの不一致、期限切れ、証拠の再利用を拒否します。本人確認成功時にチャレンジを消費しますが、それだけで削除実行を承認するわけではありません。完了レコードへの状態遷移ではチャンネル・チャレンジ・証拠・OAuth 参照を取り除き、匿名監査に必要な最小限の時刻だけを残します。既存の `users`・座席・履歴・Auth ユーザーは変更せず、D01 の削除保護処理も代替しません。

### サポート OAuth のアトミックな処理

- **`start`**: `supportChallenge` から受付レコードを特定し、同じ Firestore トランザクション内で有効な対応づけを確認して OAuth レコードを作成します（リクエスト ID・環境・目的・チャレンジハッシュを固定）。
- **`channel`**: 固定された目的と、新しく認証した OAuth で得た公開メタデータだけを返します。クライアントからの申告値は受け取りません。
- **`confirm`**: 同じトランザクションで OAuth の状態・参照・同意バージョンと、受付レコードの状態・環境・リクエスト ID・目的・旧チャレンジ無効化・対象チャンネル・期限を一括検証します。`SupportRequest` へ証拠を 1 度だけ記録し、OAuth とチャレンジを消費します（2 つの独立した OAuth からでも証拠は 1 度しか記録されません）。成功時は `purpose=support` と推測不能な `requestRef` を返し、Custom Token 発行・WebAccount 作成・Firebase セッション完了・データ削除は行いません（通常ログイン用フローへの迂回も拒否）。消費時に OAuth 内のチャンネルメタデータ・`state`・参照を消去します。
- **通常フローとの分離**: 通常レスポンスは `purpose=login` を明示し、OpenAPI で判別可能な共用体として検証します。通常ログイン用アダプターは `purpose=support` を受け付けないため、通常ログイン画面でサポート確認を行うことはできません。

### サポートのブラウザ操作と有効期間

- **既存セッションとの独立**: サポート開始時は既存の Firebase セッションがあっても通常 MyPage へ転送せず、新しい OAuth 認証を開始します。不正なチャレンジ時は専用の無効表示を出し、通常ログインへ切り替えません。
- **確認画面と完了時**: サーバーから受け取った目的と公開チャンネル名を表示し、サポート専用ボタンで確認します。成功時は推測不能な参照番号だけを受付画面のメモリへ渡し、`signIn`・`session-complete`・削除処理は呼び出しません。参照番号はルート離脱・`pagehide`・UID 変更で消去し、URL やストレージに保存しません。
- **Referer 対策**: 製品 HTML には `no-referrer` を指定し、チャレンジ等のクエリが外部遷移時の Referer に載らないようにしています（アクセスログ・CDN・Hosting 設定の実確認は公開前に実施します）。
- **処理の世代管理**: サポートの `confirm` は、本人・ページライフサイクル・確認操作の世代に紐づきます。ログアウト・UID 変更・同一 UID での再ログイン・`pagehide`・アンマウント・新しい確認操作で旧リクエストを中断し、`pageshow` でも復活させません（サーバー上の証明済みレコードを取り消すのではなく、ブラウザ側での無効な表示・遷移を抑止する仕組みです）。

### 運用担当者向けの読み取り専用エミュレーター診断

`cmd/mypage-operator-dryrun` は、合成データを入れたローカル Firestore エミュレーター専用の読み取り専用診断 CLI です。

- **実行制約**: `development` 環境・明示した `demo` プロジェクト・ループバック接続先・目的（`delete` / `revoke` / `disclosure`）を必須とし、認証情報ファイル・実プロジェクト・本番・実行用引数を拒否します。受付参照はサイズ制限付き標準入力からのみ受け取り、引数やログに出しません。ADC・Google API・Auth 失効・通知・書き込み機能は持ちません。
- **照合内容**: 単一の読み取り専用トランザクションで、受付レコード・消費済みサポート OAuth・受付インデックスを照合します。通常ログインや不一致・期限切れは拒否します。OAuth 追跡記録が TTL で消去されている場合は `proofTrace=unknown` として報告し、証拠フィールド欠如や不整合は拒否します。
- **出力制限**: 時刻・状態・目的・スコープ付き件数だけを出力し、チャンネル ID・受付 ID・チャレンジ・証拠・氏名・作業内容・生エラーは出しません。文書 ID は最大 1,001 件まで取得し、1,000 件超は `at_least=1001`、取得失敗や未確認ストアは `unknown`（`0` にはしない）とします。また `readOnly=true`、`executionAuthorized=false`、`inventoryComplete=false` を常に明示します（Auth・キャッシュ・バックアップ・BQ・ログ等は確認対象外のため）。

```sh
# system/ ディレクトリから実行
GOOGLE_CLOUD_PROJECT=demo-youtube-study-space-ci \
MYPAGE_ENVIRONMENT=development MYPAGE_SUPPORT_PURPOSE=delete \
FIRESTORE_EMULATOR_HOST=127.0.0.1:8080 \
go run ./cmd/mypage-operator-dryrun < /path/to/private-synthetic-reference
```

※参照ファイルはアクセス制限のある手元の場所に保管し、リポジトリ・PR・CI 成果物には含めないでください。

## 任意のアクセス解析と同意

### 同意管理とセキュリティ方針

- **同意状態**: `unset` / `granted` / `denied` の 3 状態で管理します。`unset` 時は操作を妨げない同意バナーを表示し、未選択・拒否でも主要機能を利用できます。ファーストパーティーストレージには `granted` / `denied` の文字列だけを保存し、UID やチャンネルと結び付けません。
- **変更と別タブ同期**: Cookie 設定画面からいつでも変更でき、`storage` イベントで他タブの拒否を受信した場合も即座に送信を停止します。ストレージ保存に失敗しても現在のページ選択は適用し、失敗メッセージを表示します。
- **送信制限（`AnalyticsGate`）**: 同意前は初期化・送信を行わず、同意前のイベントをキューに貯めて再送することもしません。送信対象は固定ルート・タイトル・完全一致した公開 UTM のみとし、コールバック・`code`/`state`/`error`/`supportChallenge`・任意クエリ・フラグメント・生 `referrer`/`title`・個人データは渡しません。通常ログイン時はパラメーターなしの 4 イベントだけを扱います。
- **読み込み条件と公開ヘッダー**: 実ローダーは測定 ID が設定され、公開オリジンがブラウザのオリジンと一致する環境で、同意後にスクリプトを読み込みます（必須の Firebase / App Check / reCAPTCHA 通信とは別同意）。全 API レスポンスには `no-store` / `nosniff` / `no-referrer`、`default-src 'none'` / `frame-ancestors 'none'`、不要なデバイス権限の拒否を設定します。

### モックで検証できる GA4 コマンドアダプター（`GA4Sender`）

- `AnalyticsGate` からだけ開始する同期アダプターで、コンストラクターでは識別子やグローバル変数を作りません。
- 開始時に `config` による自動ページビューと広告シグナルを無効化し、固定オリジンのルート URL・空の `referrer`・空の `title` を指定します。
- 送信時も安全なルート・固定タイトル・許可済み UTM を再検証し、停止時はコンテキストを消去して測定無効化フラグを設定します。`denied` 変更時は送信を誘発し得る `gtag` コマンドを呼ばず、同意前のイベントも再送しません。
- **検証の限界**: `GA4Sender` 自体は通信を行わないため、モックテストはコマンド引数と無効化順序の検証にとどまります。`send_page_view=false` だけでは履歴変更時の自動ページビューを防げないため、GA4 管理画面側で Enhanced Measurement の無効化・14 か月保持・保持期間リセット OFF・全タグ一覧・実通信の非送信を公開前に確認します。

### 同意に連動する GA4 ローダー（`ConsentTag` / `browserTagLoader`）

- `ConsentTag` は `granted` の場合だけブラウザローダーを起動し、読み込み前後のキュー再送は行いません。撤回・アンマウント時は送信を止めて保留コマンドを消し、旧読み込みのコールバックが新しい同意世代を上書きしないようにします。
- `browserTagLoader` は専用の単一 `dataLayer` を使用し、スクリプト挿入前に同意・設定を初期化します。固定の `gtag.js` URL、`no-referrer`、5 秒のタイムアウトを使い、共有タグやグローバル変数に既存の所有者がいる場合は読み込みを拒否します。撤回後に再同意しても読み込み済みスクリプトは再取得しません。
- リリース設定には `VITE_MYPAGE_GA4_ID` と `VITE_MYPAGE_PUBLIC_ORIGIN` が必須です（未設定のローカル環境では読み込みません）。スクリプト要素を除去しても実行済みコードは取り消せないため、実環境でのコンソール・通信確認を公開前に行います。

## メタデータの保持と失効

### 公開チャンネルメタデータの更新

- **取得方法**: サーバー専用の API キー（`MYPAGE_YOUTUBE_API_KEY`）を使い、固定の YouTube エンドポイントから取得します（OAuth トークンは使いません）。検索タイムアウトは 1 秒とし、リダイレクトを追わず、リクエスト URL や生エラーを公開しません。
- **更新と 30 日期限**: 外部呼び出しはトランザクション外で行い、Firestore の文書リビジョンとポリシー・アクセス状態をトランザクションで確認して既存アカウントの公開メタデータだけを更新します（新規作成はしません）。取得から 30 日経過したメタデータは検索前に同じリビジョン保護で除去します（同意や本人情報、アクセス状態は保持し、`metadataFetchedAt` も消去）。
- **失敗・表示停止時の扱い**:
  - 認証や同意が失効した場合はスナップショット取得前に停止します。上流 API の失敗時は「一部取得」または「取得不能」とし、作業時間を `0` に変換しません。
  - メタデータの表示停止（`METADATA_TOO_OLD`）が必要と判明した場合、たとえ作業スナップショットの取得・集計に失敗しても、既存の `200` 一部取得レスポンスでアカウントの `METADATA_TOO_OLD` を返し、現在・集計・7 日の各項目を `SOURCE_UNAVAILABLE` とします（キャッシュ不可）。ブラウザはこの理由を受け取ると旧アカウント表示だけを削除し、旧作業データと `asOf` は古い値として保持します。通常の作業取得障害は従来どおり `503` を返します。

### プロセス間でのメタデータ表示停止

- **チャンネル不在の判定条件**: 公開 API が HTTP `200` を返し、かつ「明示的な `items: []`」または「`items` が省略（`null` 含む）され `pageInfo.totalResults` が数値 `0`」の場合だけをチャンネル不在とみなします（YouTube Data API は 0 件時に `items` を省略し得るため `fields` に `pageInfo(totalResults)` を含めています）。`{}`、必須フィールド欠落・非数値・負数・非ゼロ、`nextPageToken` ありの応答は一時的な失敗として区別します。
- **不在時の消去とプロセス間共有**: チャンネル不在と判明した場合は期限前でもリビジョン・ポリシー・アクセス状態を確認して公開メタデータと取得日時を消去します（消去に失敗してもレスポンスには表示しません）。メタデータが空のアカウントは `METADATA_TOO_OLD` として返し、BFF キャッシュと singleflight は `WebAccount` のリビジョンとメタデータ有無に結び付けるため、別プロセスでの消去後に古いキャッシュが再利用されることはありません。

※既存の全ブラウザへの即時プッシュ通知や、アカウント削除に対するすべての書き込み保護を代替するものではありません。

### 未利用アカウントのメタデータ削除と監視

- **`MetadataCleanupJob`**: 利用時の再取得とは独立して動作し、`metadataFetchedAt` から **29 日以上** 経過したアカウントをページ単位で処理します。公開メタデータと取得日時の 4 フィールドだけを削除し、`updatedAt` を更新します（本人情報・同意・`firstWebLoginAt`・アクセス状態は変更せず、OAuth や API による再取得・新規作成も行いません）。
  - 実行単位: プロジェクトを明示したうえで、時刻と文書 ID による安定したページ分割、最大 1,001 件の検出、必要フィールドのみの取得、リビジョン完全一致のトランザクションを使用します。
  - 失敗条件: 並行更新された項目は上書きせず `changed` / `missing` として扱い、最終再走査での残存・ページ上限到達・10 分の制限時間超過・エラー発生時は成功とみなしません（次回は現在リビジョンから再実行可能）。30 日以上のデータが残っていた場合は保持期限違反を匿名件数で記録します。
- **`MetadataCleanupRunner` と健全性監視**:
  - [MetadataCleanupRunner](../../system/core/mypage/metadata_cleanup_runner.go) の `Run` は削除ジョブと監視状態の永続化・健全性シグナル出力を実行し、`CheckHealth` はアカウントに触れない独立監視用コールバックとして動作します。削除ジョブの起動漏れも検知するため、両者を別々のスケジュール（削除ジョブは開始間隔 23 時間未満・例として 1 日 2 回、独立監視は毎時など）で呼び出す想定です。
  - [FirestoreMetadataCleanupMonitor](../../system/core/mypage/metadata_cleanup_monitor_store.go) はサーバー専用の `mypage-maintenance/metadata-cleanup` 単一文書へ、最新観測・成功走査の開始時刻・未受理の期限違反開始時刻をトランザクションで保存します。時刻はマイクロ秒精度に正規化し、遅延到着の古い走査で新しい失敗を上書きせず、破損状態は初期化せず拒否します。
  - 健全性評価（`EvaluateMetadataCleanupHealth`）は、成功実績なし・実行失敗・保持期限違反・成功した走査の開始時刻（`StartedAt`）から 23 時間以上のハートビート欠如を警告します。
- **出力先の制約（`JSONMetadataCleanupRecorder`）**: 開始・完了時刻、結果、固定段階名、件数だけを出力し、ID・メタデータ・生エラーは出しません。2 秒の書き込み期限を適用するため、期限制御が有効な専用パイプやソケット等だけを許可し、通常ファイルや標準出力は安全のため拒否します。出力先が期限違反を受理した後にだけ、想定時刻を比較してトランザクションで ACK します。

接続例と残っている運用上の確認事項は [メタデータ監視の実装・接続手順](release/metadata-monitoring.md) を参照してください。

## Hosting

`mypage/src/hosting.ts` の `hostingCandidate` は、指定された環境・プロジェクト・対象・Cloud Run サービス・リージョン（`development` は `asia-southeast2`、`production` は `asia-northeast2`）と、レビュー済みの SDK 接続先から設定候補だけを生成する純粋関数です。既存の `firebase/firebase.json` は変更せず、CLI の実行も行いません（`public: "dist"` は `mypage/` 基準）。

- **ルーティングと書き換え**:
  - `/privacy_policy` → `/privacy` へ HTTP 302 リダイレクト
  - `/api` および `/api/**` → Cloud Run へ転送
  - `/privacy` および `/terms` → ビルド時に生成した静的規約 HTML へ書き換え
  - その他 → SPA（`index.html`）へ書き換え
- **キャッシュとセキュリティヘッダー**:
  - 既定では全パスに `no-store` / `no-referrer` / CSP / セキュリティヘッダーを設定します。
  - `hostingCandidate(input, assetPaths)` に実ビルドの全ファイル一覧を渡した場合だけ、既知のハッシュ付き JS・CSS・`woff2` の完全一致パスを `public, immutable` にします（HTML・API・未知のハッシュパスは `no-store`）。
  - CSP は明示した HTTPS 接続先だけを許可し、wildcard・`unsafe-inline`・`eval`・認証情報・クエリ・フラグメントを拒否します。
  - `validateHostingAssets` は静的ファイルと API パスの衝突、ソースマップ、秘密ファイル向けパスを拒否します。Cloud Run API 自身のレスポンスヘッダーも保持します。

原価の前提は [増分原価モデル](cost-notes.md) を参照してください。実 SDK・reCAPTCHA・GA4 の通信一覧、Hosting の実ヘッダーとアクセスログ除外、カスタムドメインの HSTS は対象リリースの配備時に別途検証します。
