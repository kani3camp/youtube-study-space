# Privacy request intake (source-only, disabled)

## Task contract

**Goal:** A signed-in user can submit one in-app privacy request, receive a receipt before fresh support OAuth, and read an operator response after that proof. A restricted user with a valid existing Firebase identity retains this narrow path. The public Contact page provides the configured reply-capable human exception path when no usable session exists.

**Invariants:** The server derives the target channel from a verified custom-provider Firebase uid. App Check and fixed Origin/Host checks apply. Browser purpose is an allowed request category, never an execution authority. The support OAuth transaction still binds the server-owned purpose, environment and target, consumes proof once, and never mints a Custom Token or WebAccount. Neither intake nor status executes deletion, disclosure or revoke. A delete receipt's acceptedAt and existing seven-calendar-day deadline stay fixed across retries and challenge reissue. Public Home, Privacy, Terms and Contact routes remain accessible. No anonymous auto-create or new Google scopes/email collection.

**Non-goals:** Production wiring, actual operator response delivery, the cross-store deletion run, SLA/policy changes, a bearer status link, and a no-session automated reply mechanism.

**Acceptance:** Default-off server returns 503 for intake. When explicitly enabled with a stable per-environment server secret, the two routes require App Check and a valid Firebase custom uid; neither runs the normal MyPage ServiceAccessControl/account/consent gate. Unknown fields, duplicate fields, wrong purpose and forged channel fields fail. Exact retries, including ACK loss and concurrent submit, return the same receipt/challenge; changing content with the same key yields 409. A separate key is a separate claim. Status and reply require both matching uid and completed support OAuth proof; guessed refs, other environments and preproof views fail. 429 includes Retry-After.

**Verification:** Go unit/race/lint, Firestore Emulator transaction tests, frontend typecheck/build/tests/check, OpenAPI contract check and synthetic browser QA where available. All data and replies in tests are synthetic.

Synthetic browser view: run `VITE_PUBLIC_PRIVACY_CONTACT_URL=https://contact.example.invalid/privacy pnpm dev --host 127.0.0.1 --port 18081` in `mypage/`, then `python scripts/privacy-intake-qa.py --output /tmp/mypage-privacy-intake-qa`. The dev-only runtime injects synthetic credentials and replies; external requests are blocked. This is not a real Firebase/Google/Hosting test.

## Storage and response boundary

`FirestorePrivacyIntake` is injected only when `ServerConfig.EnablePrivacyIntake` is true and a server-only secret of at least 32 bytes is supplied. Its HMAC derives independent opaque request ref, request ID and challenge from environment, uid and submission key. The key is generated in browser memory, retained through a failed send on the same form, and never logged or placed in the URL. The HMAC secret must remain stable while retries are supported. The Firestore transaction creates `support-requests`, `support-challenges` and `support-request-ids` together. It reads the same document for retries and compares the exact purpose/body fingerprint. The challenge is returned only while the original awaiting-proof challenge remains valid. Normal support OAuth uses the existing one-use challenge flow. The form does not auto-retry OAuth confirm.

The in-memory draft and submission key survive internal Back navigation, so a late response after leaving the form is ignored and an intentional retry uses the same key. Inputs are fixed while a submit or status lookup is pending. UID changes, signout and pagehide clear the draft, status ref, proof display and pending UI state; an earlier identity's late response cannot repopulate them. A full OAuth redirect starts a new browser runtime, so the support confirm response carries two distinct values: existing `requestRef` remains the proof receipt, and optional `supportRequestRef` is the original request document ref for the status view. The server reads that ref from the bound, consumed support transaction; the browser does not supply it at confirmation. Older support confirmations without the new field remain valid, with manual entry of the original intake receipt ref for status lookup. The new backend response is required before the frontend can restore the status ref automatically after OAuth redirect.

The request body and operator reply are server-only fields on `SupportRequest`. The [source-only trusted operator package](support-operator.md) replaces the bare `SetReply` boundary with a fail-closed authority interface, transactional audit and purpose-specific completion cleanup. No production identity adapter or live delivery is connected. `Status` is a POST with a ref in the body, no URL query. It checks the verified Firebase uid against the server record and requires support OAuth proof; the ref alone does not authorize a response. The server does not expose a public operator-write API.

The intake-specific process-local buckets are 6/minute burst 3 per IP before App Check/ID-token verification and 2/minute burst 2 per uid after verification, in addition to existing global buckets. These are engineering defaults, not Canon quotas. Distributed limits, verified proxy IP extraction and adaptive abuse monitoring remain release work.

## Decision and operational gates

A no-session in-app status/reply credential would alter the current Canon support OAuth result and create a new bearer or temporary session security model. This package does **not** create that credential. A user without a usable Firebase session, including someone whose Firebase account has already been deleted, must reach a configured human-triaged reply-capable privacy contact. The in-app status path is available to an existing valid session even while ServiceAccessControl restricts ordinary MyPage. It requires fresh support OAuth proof before showing an operator reply. A channel ownership transfer after proof and session persistence remain the Canon 04 residual risk; response content must be reviewed before real delivery. The completed record is anonymized, so subsequent correspondence uses the human contact.

Keep both server `EnablePrivacyIntake` and frontend `VITE_PRIVACY_INTAKE_ENABLED` off until a real exception contact and operator response workflow are configured and tested, D03 and public copy are resolved, trusted Hosting/Cloud Run/Firestore/App Check path is verified, and the 7-day deletion/backup/runbook gate is operational. D02's design choice was settled on 2026-10-09: do not add refresh-token storage or periodic polling solely to detect an external Google grant cancellation. Its YouTube policy compliance and the treatment of already retained API data after cancellation remain unconfirmed and require verification/compliance review against the actual flow before release; the settled choice is not publication approval. A public URL or feature flag alone is not evidence of those gates. Do not run live deletion, OAuth grants or production deploy from this package.
