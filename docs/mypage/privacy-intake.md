# Privacy request intake (source-only, disabled)

Canon 05/09では、返信できる有人のプライバシー窓口と、申請に結び付けた新たなOAuth認証・既存の非公開CLI・手順書を初期公開の手段としている。任意のアプリ内受付機能は無効のままとし、フォームや返信UIの有効化は初期公開の必須作業に含めない。運用担当者用CLIと削除CLIには実環境用アダプターがなく、実際の申請は処理できない。

## 用途と制約

ログイン済みの利用者はアプリ内でプライバシー申請を1件送信できる。新たなサポートOAuth認証の前に受付情報を受け取り、本人確認後に運用担当者の返信を読める。有効な既存Firebase認証がある利用制限中の利用者も、この限定的な手段を使える。利用可能なセッションがない場合、公開Contactページは、設定済みの返信可能な有人窓口を例外時の連絡先として案内する。

サーバーは、検証済みのFirebase custom-provider uidから対象チャンネルを決める。App Checkと固定Origin/Hostの検証を適用する。ブラウザが指定する目的は許可された申請区分であり、実行権限ではない。サポートOAuthトランザクションは引き続き、サーバーが管理する目的・環境・対象を固定し、本人確認の証拠を一度だけ消費する。Custom Tokenの発行やWebAccountの作成は行わない。受付と状態照会のどちらも、削除・開示・失効を実行しない。削除申請のacceptedAtと既存の7暦日の期限は再試行やチャレンジ再発行でも維持する。公開のHome・Privacy・Terms・Contactルートは利用可能なままとする。匿名の自動作成、新しいGoogleスコープ、メールアドレス収集は追加しない。

受入条件: 初期状態ではサーバーの受付処理は無効で、503を返す。環境ごとに安定したサーバーシークレットを用意して明示的に有効にした場合、2本のルートはApp Checkと有効なFirebase custom uidを必須とする。どちらも通常MyPageのServiceAccessControl・アカウント・同意の検証は実行しない。未知・重複フィールド、不正な目的、偽造したチャンネルフィールドを拒否する。ACK消失や同時送信を含め、同一内容の再試行は同じ受付情報とチャレンジを返す。同じキーで内容を変えると409を返し、別キーは別の申請として扱う。状態・返信の照会にはuidの一致とサポートOAuthの本人確認完了を必要とする。推測した参照、別環境、本人確認前の閲覧は拒否する。429にはRetry-Afterを付ける。

フロントエンドの実行時検証は、`mypage/`で`pnpm test -- src/privacy-intake.test.ts`を実行する。既存の[受付テスト](../../mypage/src/privacy-intake.test.ts)はブラウザセッションとHTTP応答をモックにし、送信内容、本人の変更、不正な状態レスポンス、OAuth遷移後にサーバーで結び付けた受付情報を検証する。

## 保存内容とレスポンス

`FirestorePrivacyIntake`は`ServerConfig.EnablePrivacyIntake`がtrueで、32バイト以上のサーバー専用シークレットを渡した場合だけ組み込む。HMACは環境・uid・送信キーから、内容を推測できない独立した申請参照・申請ID・チャレンジを導出する。キーはブラウザのメモリで生成し、同じフォームの送信失敗時も保持する。ログやURLには出さない。再試行を受け付ける間、HMACシークレットを安定して維持する必要がある。Firestoreトランザクションで`support-requests`・`support-challenges`・`support-request-ids`をまとめて作成する。再試行では同じ文書を読み、目的と本文のフィンガープリントを完全一致で比較する。チャレンジは、元の本人確認待ちチャレンジが有効な間だけ返す。通常のサポートOAuthは既存の一度限りのチャレンジ処理を使う。フォームはOAuthのconfirmを自動再試行しない。

メモリ内の下書きと送信キーはアプリ内の「戻る」操作でも保持する。フォーム離脱後の遅い応答は無視し、意図的な再試行では同じキーを使う。送信や状態照会の処理待ち中は入力を固定する。UID変更・サインアウト・pagehideでは、下書き・状態参照・本人確認表示・処理待ちUIを消去し、以前の本人への遅い応答で復活させない。OAuthの全画面リダイレクトではブラウザランタイムが新しくなるため、サポート確認のレスポンスは異なる2つの値を持つ。既存の`requestRef`は本人確認の受付参照を維持し、任意の`supportRequestRef`は状態表示に使う元の申請文書参照を示す。サーバーは対応づけ済み・消費済みのサポートトランザクションからこの参照を読み、ブラウザは確認時に指定しない。新フィールドのない旧確認レスポンスも有効とし、元の受付参照を手入力して状態照会できる。OAuthリダイレクト後にフロントエンドが状態参照を自動復元するには、新しいバックエンドレスポンスが必要である。

申請本文と運用担当者の返信は、`SupportRequest`のサーバー専用フィールドに置く。[信頼済み運用担当者向けの実装パッケージ](support-operator.md)は、直接の`SetReply`呼び出しを、検証不能なら拒否する権限インターフェース、トランザクション内の監査、目的別の完了時消去に置き換える。本番の本人識別アダプターや実配送は未接続である。`Status`は参照を本文に含むPOSTとし、URLクエリには含めない。検証済みFirebase uidをサーバーレコードと照合し、サポートOAuthの本人確認を必須とする。参照だけでは応答を許可しない。公開の運用担当者用書き込みAPIは提供しない。

受付専用のプロセス内制限は、既存の全体制限に加えて適用する。App Check・IDトークン検証前のIP単位では毎分6回・バースト3回、検証後のuid単位では毎分2回・バースト2回とする。これは技術上の既定値であり、Canonの利用枠ではない。Canon S01では、承認済みの開発用Hosting→Cloud Run経路で、実IPの識別、XFF偽装、429の分離を先に確認する。IP抽出方法はその証拠に基づいて変更する。分散制限、Redis、WAFは初期段階の前提条件にしない。

## 運用上の判断と公開条件

セッションなしでアプリ内の状態や返信を読む認証情報を導入すると、現在のCanonが定めるサポートOAuth結果が変わり、新しいBearer認証や一時セッションのセキュリティモデルが必要になる。このパッケージでは導入しない。Firebaseアカウント削除済みの利用者を含め、利用可能なFirebaseセッションがない人には、人が対応し返信できる設定済みのプライバシー窓口を案内する。アプリ内の状態照会は、有効な既存セッションがあれば、ServiceAccessControlで通常MyPageが制限されていても利用できる。運用担当者の返信を表示する前に、新たなサポートOAuthの本人確認を必要とする。本人確認後のチャンネル所有権移転とセッション維持はCanon 04の残留リスクであり、実際に返信する前に内容を確認する必要がある。完了レコードは匿名化されるため、その後の連絡は有人窓口で行う。

初期の有人窓口での公開では、サーバーの`EnablePrivacyIntake`とフロントエンドの`VITE_PRIVACY_INTAKE_ENABLED`を両方とも無効にしておく。後からこのUIを有効にする場合は、実際の連絡先、運用担当者の返信・配送手順、D03の公開文面、信頼済みHosting/Cloud Run/Firestore/App Check経路、削除・バックアップ・手順書の証拠を別途必要とする。初期公開条件を満たしても、フラグは有効にならない。セッションなしの場合は同じ有人窓口を使い、状態照会用Bearer認証情報は追加しない。D02の設計方針は、外部のGoogle権限取消を検出するためだけにリフレッシュトークン保存や定期取得を追加しないことである。アプリ内とGoogle設定の両方からの取消に対する規約適合性は、保持済みAPIデータの扱いを含め未確認である。実ユーザーの受入前に検証・規約適合性レビューで解決する。そのレビューに先回りして新しい取消UIやAPIを追加しない。公開URLや機能フラグだけを、条件を満たした証拠として扱わない。このパッケージから実削除・OAuth権限付与・本番配備を実行しない。
